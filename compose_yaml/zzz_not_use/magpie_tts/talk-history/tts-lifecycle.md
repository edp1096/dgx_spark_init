# 같은 Spark의 TTS 수명 관리

2026-10-06 관리형 Magpie TTS를 이미지·ASR·Media의 공통 작업 큐에 연결했다.
QAD 세트는 LLM을 먼저 기동하고 TTS는 실제 음성 요청에 기동한다. 연속 요청은
프로세스를 재사용하며 마지막 작업 후 2분 유휴 또는 메모리 부족 시 종료한다.
음성 설정·원본 FP16 가중치·코덱·기존 긴 문장 패치·언어/한자 처리는 유지한다.

2026-10-07 EXL3 세트는 이미지·ASR·TTS를 LLM 다음에 기동하고
`keep_resident: true`로 유지한다. 같은 프로세스를 계속 재사용하며 유휴 타이머와
메모리 압박 회수 대상에서 제외한다. 메모리가 부족한 새 요청은 상주 모듈을
종료하지 않고 거절한다. 명시적인 서비스 종료·세트 변경은 가능하며, QAD의
기존 요청 시 기동·2분 유휴 종료 정책은 유지한다.

## 요청과 종료의 보호

Talk의 작업 사용 수에는 큐에서 기다리는 TTS 요청도 포함한다. 요청이 큐에
들어가기 전에 사용 수를 올리고 모든 문장의 PCM 응답을 소비할 때까지 유지한다.
취소·실패 시에도 실행 중인 네이티브 요청을 임의로 중단하지 않는다.

네이티브 서버는 `/v1/runtime/memory`에 실행·대기 수와 마지막 작업 완료 후
유휴 시간을 반환한다. 종료 직전 `/v1/runtime/quiesce`로 새 입장을 막는다.
요청 수 검사와 새 요청 입장은 같은 mutex로 보호한다. 실행·대기가 있으면
quiesce는 409, 성공한 quiesce 이후 음성 요청은 503을 반환한다.
종료를 취소하면 `/v1/runtime/resume`으로 입장을 다시 허용한다.
상태 조회 실패·불명 상태는 회수하지 않고 재확인한다.

HTTP worker 4개로 추론 중에도 상태·종료 API가 응답한다. 기존 비선점 모드의
추론은 별도 gate로 직렬화하고 네이티브 대기 작업도 사용 수에 포함한다.
GPU 본체·코덱의 가중치 형식이나 추론 커널은 수정하지 않는다.

## 예산과 설정

이미지는 `sparktalk-magpie-tts:v2607-longform3-lifecycle`, NeMo-Speech.cpp는
기존 고정 커밋 `7752dabb3453ec7c5fd751e5e2052650aaa20497`을 사용한다.
전체 서비스 예산 3GiB, 추가 작업 여유 하한 1.5GiB, CUDA 기동 예산 1.5GiB다.
더 큰 사용자 예산은 유지한다. 이 값은 입장 검사용 예산이며 모든 입력의
실제 최대 메모리 사용량을 보증하지 않는다. 기존 1.2GiB 예산은 3GiB로 갱신한다.

CPU 메모리 상한과 swap 포함 상한을 모두 112GiB로 설정해 컨테이너 swap을
금지한다. CUDA/통합 메모리 전체를 cgroup 상한만으로 보호한다고 취급하지
않으며 실제 시스템 여유 검사도 유지한다. 종료된 보조 모델의 파일 캐시만
선택적으로 회수하고 LLM 체크포인트·KV나 전역 페이지 캐시를 비우지 않는다.
Qwen Image 2.1과 함께 쓰는 부가 모델의 새 CUDA 기동에는 즉시 Free 메모리
10GiB도 검사한다. 이 조건은 이미 기동한 서비스의 연속 요청에는 적용하지 않는다.
가용량이 충분해도 Free가 부족하면 유휴 서비스와 닫힌 보조 가중치 캐시를
회수한 뒤 다시 검사한다. 10GiB는 이번 기동 검증의 보수적인 입장 조건이다.

기존 기본 로컬 Magpie 구성에 QAD 멤버십을 추가하되 사용자의 TTS 활성화·음성
선택·사용자 배치는 보존한다. 이번 운영 적용은 TTS를 활성화하고 endpoint를
`http://127.0.0.1:8692`로 지정했다. 1M 컨텍스트, MTP 3, ASR 화자 구분,
이미지 생성 설정과 답변 자동 재생 선택은 유지했다.

## 검증 기록

### EXL3 상주 검증

2026-10-07 실행 중인 EXL3의 실제 1,048,576 문맥·Q8 KV와 MTP 3 설정을
유지했다. 이미지·ASR·TTS를 기동하고 실제 작업으로 준비한 뒤 이미지 기준
131.01초 유휴 구간을 확인했다. 세 서비스의 PID 2235994·2237610·2238155와
EXL3 PID 1267314가 유지됐고 다음 작업도 같은 프로세스로 완료했다.

- 1024×1024 이미지: 최초 36.71초, 유휴 후 27.17초.
- 한국어 TTS: 최초 0.70초, 유휴 후 0.68초.
- 생성한 약 8.17초 음성의 Talk 전사: 최초 3.75초, 유휴 후 1.14초.

음성은 Talk HTTP 핸들러, 이미지는 같은 프로덕션 도구와 실제 컨트롤러의
입장 검사 경로로 측정했다. ASR 속도는 음성 입력 전사이며 긴 파일·화자 구분
속도를 뜻하지 않는다. 가용 메모리는 준비된 유휴 상태에서 약 23GiB였다.
이미지 2장과 WAV 2개를 운영 Talk의 **EXL3 상주 이미지·ASR·TTS 검증 · 2026-10-07**
대화에 저장하고 다운로드 SHA-256을 확인했다. 원시 측정은
`~/.cache/model-download-jobs/exl3-resident-aux-20261007/`에 보관한다.

Go 전체 테스트, 관련 config/orchestrator/server/tts race 테스트, 웹 테스트와
빌드, 독립 Compose·내장 자산 동기화 검사를 통과했다. 수명 회귀 시험은 연속
재사용·취소된 대기자·압박 회수·실행/대기/불명 상태·회수 중 새 대기자를 확인한다.

실제 네이티브 동시 긴 문장 요청에서 대기 수가 증가했고 quiesce 409를 확인했다.
요청 완료 후 quiesce 200 → 새 음성 요청 503 → resume 200을 확인했다.
잘못된 JSON 요청 후에도 사용 수가 정상으로 돌아왔다. 연속 요청은 같은 PID였다.
운영 Talk의 최초 요청·동시 대기 요청 2개도 완료하고 같은 PID를 유지했다.
최초 준비 시간에는 한 번 수행하는 GGUF 변환 준비가 포함되었다.

전체 원시 기록과 음성은 `~/.cache/model-download-jobs/tts-lifecycle-20261006/`에
보관한다.

## QAD 1M 통합 운영 실측

최종 운영 바이너리에서 QAD를 먼저 기동하고 `/server_info`로 설정 문맥·실제
KV 모두 1,048,576, MTP steps 3을 확인했다. 같은 컨트롤러의 Talk 이미지 도구,
전사 경로, TTS HTTP 핸들러에 요청을 동시에 제출해 모두 완료했다.

- 1024×1024 이미지 생성: 88.53초. 새 서비스 준비와 큐 대기가 포함된다.
- 30초 음성 전사·화자 구분: 96.72초, 전사 280바이트, 화자 구분 `completed`.
  이미지 대기·Media 추출·ASR 기동을 포함하며 순수 추론 시간과 구분한다.
- TTS 최초 요청: 7.15초. 다른 작업 후 합성 7.80초·1.01초, 동일 PID 3958651.
- 운영 Talk HTTP 연속 합성: 0.94초·0.76초, 동일 PID 3958651.
- 마지막 요청 후 121.09초에 유휴 종료. 다음 요청은 새 PID 3973855로
  4.84초에 완료했다. 종료 전후 시스템 가용량 차이는 약 2.10GiB이며 주변
  호스트 활동도 포함한 관측값이다.

모든 단계 후 QAD PID 3751541과 실제 1M KV·MTP 3이 유지됐다.
최종 통합·유휴·재기동 전체 측정의 최소 가용량은 10.35GiB, 최소 Free는
3.01GiB다. 시스템 스왑 쓰기는 0바이트, 읽기는 7,962,624바이트였다.
네 모델 cgroup의 측정된 `memory.swap.current`, `oom`, `oom_kill`은 모두 0이다.
Free 10GiB는 새 CUDA 기동 직전 조건이며 추론 내내 유지하는 하한이 아니다.

압박 회수는 실제 작업 간 경쟁으로도 관측했다. 추가로 메모리 probe에 1GiB를
주입한 시험에서 실제 유휴 TTS의 quiesce와 Docker 종료를 확인했다.
이 추가 시험은 메모리 스트레스 할당 없이 회수 분기를 검증한 것이다.
QAD PID·실제 KV·MTP는 이 시험 뒤에도 유지됐다.

초기 조사에서는 CUDA 기동 실패와 시스템 스왑 쓰기 증가가 있었다.
작은 cgroup 상한, SHA 검사 후 재충전된 이미지 파일 캐시, 디코딩 완료 후
Media 재기동 경로를 보완했다. 실패 시도 로그도 `failed-*`로 보존했다.
최종 성공 시험의 스왑 쓰기 0을 모든 입력이나 초기 조사 전체의 결과로 확대하지 않는다.
이번 검증은 실제 1M KV 할당과 부가 작업 동작 검증이며 1M 토큰 전체 prefill 시험은 아니다.

생성 이미지 3장과 WAV 15개는 운영 Talk의
**QAD 1M·이미지·ASR·TTS 통합 검증 · 2026-10-06** 대화에 보관하고
다운로드 SHA-256을 확인했다. 성공 시험 결과와 초기 조사 중 생성에 성공한
결과물도 함께 보관했다. 시험 후 모델을 종료하고 기존 Extra SSH·Media를 복구했다.
