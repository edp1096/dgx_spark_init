# QAD HiCache 실험

기존 SGLang 캐시에 target/MTP KV·QSA와 Mamba·PLE 상태를 함께 저장합니다.
대화의 토큰 비교 규칙은 유지하고, 파일 크기·스키마·CRC32 검사를 추가했습니다.

**1M 추론과 GPU 캐시 재사용은 확인했지만, 1GB 호스트 풀로 1M 전체를 디스크에서 복원하는 기능은 미완성입니다. 운영 기본값은 꺼져 있으며 공개 `sm121-v5`에는 이 실험 패치가 없습니다.**

## 사용 범위

- 로컬 소스의 `qad-tp1` 빌드 대상, TP1/PP1/CP1, `file`, `page_first`만 지원합니다.
- `SGLANG_QAD_HICACHE=1`, `--enable-hierarchical-cache`, `--hicache-storage-backend file`, `--hicache-mem-layout page_first`, 명시적인 `--hicache-size`가 필요합니다.
- 저장 경로는 `SGLANG_HICACHE_FILE_BACKEND_STORAGE_DIR`로 지정합니다. 가중치나 수치 계산 설정을 바꾸면 별도 경로를 사용합니다.
- 파일 이름에 `qad-complete-v2`를 붙여 이전 형식과 분리합니다. 독립적인 MTP PLE 풀과 ReplaySSM은 미지원입니다.
- 호스트 풀 예산에는 부가 상태가 포함되며, 전송·직렬화 임시 메모리는 별도입니다.

## 검증 결과

DGX Spark, 1M 설정, MTP 3단계/4 draft tokens, ko64k, 호스트 풀 1GB 기준입니다.

| 검사 | 결과 |
|---|---|
| CPU·파일·강제 종료 회귀 검사 | 17개 통과 |
| 네이티브 CUDA 상태 전송 | FP8 KV/BF16 QSA/Mamba/PLE 재배치 후 값 일치 |
| 대화 전환·분기·수정·도구 결과 변경 | 6개 사례의 출력 토큰 일치, 디스크 4,480~4,544토큰 적중 |
| 이미지·WebM | 내용 구분과 재사용 후 답변 일치 |
| Mamba/KV 파일 손상 | 손상 캐시를 버리고 재계산, 출력 일치 및 후속 요청 정상 |
| 처리 중 요청 취소 | 해당 요청 취소 후 대기 요청 정상 완료 |
| 실제 입력 길이 | 131,072 / 262,144 / 524,288 / 1,048,000토큰 처리 및 GPU 재사용 출력 일치 |
| 새 프로세스의 디스크 복원 | 53,248 입력 중 49,152토큰 복원, 출력 토큰 일치 |
| KV 상한 예약 공간 부족 | Native/OpenAI API에서 HTTP 400 반환, 후속 정상 요청 완료 |
| Qwen·Flux·ASR·TTS 동시 요청 | 모두 완료, 1,047,040 입력에서 512토큰 생성 및 1024×1024 이미지 생성 |
| LoRA 아웃페인팅 | 다른 모델을 유지한 채 640×640 출력 완료 |

동시 부하와 LoRA 검사 구간을 2초 간격으로 측정한 최소 가용 메모리는 3.24GiB였고, 시스템 스왑 쓰기는 약 2.35GiB 증가했습니다.
TTS 전체 생성 시간은 단독 요청 0.71초에서 동시 요청 9.16초로 늘었습니다. 생성 음성 길이는 5.85초입니다.
1,048,000토큰의 새 계산은 1,054.82초, GPU 재사용은 6.63초였습니다. 단일 측정값이며 입력 구조에 따라 달라집니다.

1GB 풀의 KV 용량은 54,336토큰입니다. 128K 이상 검사에서는 디스크 적중이 0이었고 재계산했습니다.
1M 전체 복원에는 작은 호스트 버퍼로 나눠 전송하는 경로가 추가로 필요합니다.
`cache_salt` 지정 요청의 디스크 재사용도 이번 고정 SGLang 경로에서는 적중하지 않아 검증 완료 범위에 포함하지 않습니다.
출력 토큰은 검사 사례에서 일치했지만 logprob는 비트 단위로 같지 않았습니다. 강제 종료 검사는 전원 장애 내구성을 뜻하지 않습니다.

상세 수치와 이미지·소스 식별자는 `hicache-qualification.json`, 회귀 검사는 `test_hicache.py`와 `test_hicache_gpu.py`에 있습니다.
