# ASR 요청별 메모리 예산

예산 측정 당시 `sparktalk-nemotron-asr:0.6b-q8-diar1` 구성의 기동 예산은 3.5GiB다. 기존 카탈로그의 6GiB는 입력을 모르는 경우의 기본 추정치로 남지만, Talk의 음성 입력·첨부 전사는 이 값을 일괄 적용하지 않는다.

1. Extra Media만 준비해 음성을 16kHz mono PCM16 WAV로 추출한다.
2. 최대 512MiB의 임시 파일로 받아 실제 추출 크기를 확인한다. 압축된 업로드 크기로 길이를 추정하지 않는다. 파일은 성공·실패 모두 삭제한다.
3. 추출 작업의 대기열 점유를 반환한 뒤 ASR 작업 예산으로 다시 대기열에 진입한다. ASR과 Media의 예산을 검사하고, 필요한 경우 유휴 FLUX를 회수한다. 실행 중인 다른 작업을 중지하지 않는다.
4. ASR 예산은 `ceil((3.75 + WAV바이트×32/2^30 + 화자구분여유)×4)/4` GiB다. 화자 구분 여유는 0.25GiB다. 추출 파일 크기·요청 모드를 사용하고, 기본값보다 큰 사용자 예산은 유지한다.
5. 이미 상주한 ASR/Media 점유는 잔여 필요량에서 차감한다. 성공 후 여유가 있으면 재사용하고 오류·취소 시에는 정리한다.

| 음성 길이 | 일반 전사 예산 | 화자 구분 포함 예산 |
|---|---:|---:|
| 2분 | 4.00GiB | 4.25GiB |
| 10분 | 4.50GiB | 4.75GiB |
| 1시간 | 7.25GiB | 7.50GiB |

이는 실측에 여유를 더한 예산이며 강제 메모리 상한은 아니다. 파일 크기에 비례해 증가하며 6GiB에서 잘라내지 않는다. 다른 ASR 구성에는 이 프로필을 적용하지 않는다.

## 측정 근거 — 2026-09-28

동일 Q8 ASR + Nemotron-3-Diarization 서버에서 공개 JFK 샘플을 반복한 30초·2분·10분·1시간 WAV를 순차 처리했다. 모든 전사/화자 API가 HTTP 200을 반환했다. GPU 프로세스와 비회수 호스트 상주량을 약 0.5초 간격으로 관측했다.

- 2분 전사 관측 피크: 3.83GiB.
- 10분 전사: 4.22GiB, 화자 구분: 4.18GiB.
- 1시간 전사: 6.97GiB, 화자 구분: 6.53GiB.
- 30초 처리 시간은 샘플 간격보다 짧아 그 구간의 피크를 확정하지 않았다.
- 1시간 일반 전사는 약 112초, 화자 구분은 약 12.5초였다.
- 스왑 증가는 관측됐다. 제로 스왑이나 모든 내용·화자 수의 피크를 검증한 결과가 아니다.

원시 기록: `~/.cache/runtime-inspection/asr-profile/`. 긴 오디오 API는 전체 업로드/float 음성 버퍼를 보유하며, ASR은 모델 위치 한계를 넘으면 내부 스트리밍 경로를 사용한다. 그래서 모델 파일 크기만으로 예산을 정할 수 없다.

Talk 실서비스 경로 검증: 1시간 MP3 입력을 추출해 전사·화자 구분 완료(127.8초, 텍스트 34,943바이트). 이어서 11초 음성 2회도 완료(1.68초/1.60초), ASR 컨테이너 PID 1062036 유지. 이 검증 전후 Qwen PID 1094479 유지. Go ASR/server/orchestrator/config race 테스트와 웹 빌드 통과.

후속 이미지 `0.6b-q8-diar2-workspace`는 가중치를 유지하고 요청 후 그래프 버퍼를 반환한다. 기존 길이별 예산은 낮추지 않았다. [후속 기록](weights-resident-runtime.md).
