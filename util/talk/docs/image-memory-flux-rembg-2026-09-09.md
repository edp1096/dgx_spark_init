# DGX Spark 이미지 도구 메모리 실측 — 2026-09-09

측정 원본·스크립트·출력은 저장소 밖 `/tmp/dgx-spark-image-memory-records-2026-09-10/image-memory-2026-09-09/`로 이동했다. 아래 파일명은 이 원본 경로 기준이다.

현재 FLUX.2 Klein 4B NVFP4를 유지하면서 배경 제거, 마스크 인페인팅, 아웃페인팅을 실행했다. 추가 LoRA는 사용하지 않았다. 배경 제거는 약 0.5~0.9GiB 추가로 가능했다. LanPaint의 추가 메모리보다 FLUX 실행 자체가 큰 비중을 차지했다.

## 측정 전 상태

OS가 보고하는 총 메모리 121.63GiB, 전체 사용량 108.55GiB, 가용량 13.08GiB. 전체 모델 4개를 정지하자 사용량이 4.62GiB로 내려갔다. 전체 사용량은 `/proc/meminfo`의 `MemTotal - MemAvailable` 기준이다.

| 모델/서비스 | 측정 전 GPU 프로세스 사용량 | cgroup 현재 메모리 | cgroup swap |
|---|---:|---:|---:|
| Qwen3.8 Flash Next / SGLang | 90.70GiB | 13.35GiB | 0 |
| Magpie TTS | 1.52GiB | 0.54GiB | 0.40GiB |
| Nemotron ASR | 1.16GiB | 0.06GiB | 0.41GiB |
| FLUX API, 가중치 미로딩 대기 | 0.17GiB | 0.89GiB | 0.25GiB |

DGX 통합 메모리에서는 GPU 수치, cgroup 수치, 호스트 사용량의 포함 관계가 다르다. 이 열들을 합쳐 모델별 실제 총량으로 취급하면 안 된다. 특히 대기 중 FLUX의 0.17GiB는 이미지 생성에 필요한 메모리가 아니다. 원본 수치는 `before-stop.json`, `after-stop.json`에 기록했다. 측정 전 swap 사용은 1.29GiB, 모델 정지 후 각 이미지 실험에서는 약 0.21GiB로 유지되어 실험 구간에 swap 증가가 관측되지 않았다.

## FLUX 실측

다른 모델은 모두 정지. 기존 이미지 `dgx-flux2-klein-nvfp4:4b`, 기존 API/ComfyUI 실행 옵션을 사용했다. NVFP4 diffusion 가중치, 기존 Qwen 텍스트 인코더와 VAE, seed 42, Euler 4 steps, batch 1. 사용자가 제공한 꿀병 사진을 입력했다.

| 실행 | 호스트 전체 피크 | 모델 정지 기준 4.62GiB 대비 | 실행 구간 시간 |
|---|---:|---:|---:|
| 기존 API 편집 1024×1024, 프로세스 재시작 후 첫 요청 | 23.05GiB | +18.43GiB | 9.15초 |
| 일반 마스크 인페인팅 1024×1024, 로딩된 모델 | 22.75GiB | +18.13GiB | 5.53초 |
| LanPaint 인페인팅 1024×1024, 로딩된 모델 | 22.85GiB | +18.23GiB | 9.25초 |
| LanPaint 아웃페인팅 1024×1024, 로딩된 모델 | 22.79GiB | +18.17GiB | 10.27초 |
| 기존 API 편집 512×512, 프로세스 재시작 후 첫 요청 | 21.15GiB | +16.53GiB | 6.43초 |
| 기존 API 편집 768×768, 512 실행 후 | 22.16GiB | +17.54GiB | 2.42초 |

첫 요청은 프로세스/모델 로딩 기준이며 디스크 캐시는 비우지 않았다. 일반 마스크 편집과 LanPaint의 피크 차이는 약 0.10GiB로, 단회 측정 오차와 캐시 영향을 감안하면 추가 메모리가 크다는 증거가 없다. 실행 시간은 늘어난다. LanPaint 내부 반복은 2회, Lambda 5, StepSize 0.2, Image First. 일반 마스크 대조군은 같은 인코딩·마스크·합성에 기본 SamplerCustomAdvanced를 사용했다.

FLUX 테스트 중 GPU 프로세스의 1초 샘플 피크는 약 7.1~7.9GiB였다. 이것만 보면 호스트 전체 증가량을 크게 과소평가한다. 마지막 편집 후 유휴 상태도 호스트 약 20.44GiB였고, FLUX cgroup 약 8.93GiB, GPU 프로세스 약 6.54GiB였다. 작업 후 모델/메모리를 회수하는 운영이 중요하다.

## 자동 배경 제거

FLUX도 정지한 상태에서 rembg 2.0.84, ONNX Runtime 1.29.0 CPUExecutionProvider, OMP_NUM_THREADS=4. 입력 1920×2560, 원본 크기의 RGBA PNG 출력, 기본 마스크 처리, alpha matting 미사용. 각 프로세스에서 모델을 한 번 로딩하고 사진을 두 번 처리했다.

| 모델 | 호스트 전체 피크 | 해당 실행 직전 대비 추가 피크 | 이미지 처리 및 저장 |
|---|---:|---:|---:|
| U²-Net 소형 u2netp, 캐시된 가중치 | 5.37GiB | +0.53GiB | 0.67~0.72초/장 |
| U²-Net 일반 u2net, 캐시된 가중치 | 5.65GiB | +0.78GiB | 0.81~0.87초/장 |

u2netp 최초 실행은 라이브러리 초기화 및 다운로드까지 포함해 추가 피크 0.88GiB, 프로세스 전체 약 20초였다. u2net 일반 모델 측정 중 짧은 미리보기 프로세스가 겹쳐 소량의 상향 오차가 있을 수 있다. 이 수치는 가중치 파일 크기가 아니라 Python/ONNX/이미지 버퍼를 포함한 호스트 증가량이다. CPU 실행도 통합 메모리를 사용한다.

두 모델 모두 앞쪽 꿀병 두 개를 분리한 실제 투명 PNG를 생성했다. 일반 모델이 이 사진에서 병 윤곽을 조금 더 선명하게 유지했고, 소형 모델도 실용적인 초안으로 보인다. 가장자리와 비닐 세부는 검수가 필요하다. 한 사진으로 일반 품질을 보장하지 않는다.

## 결과 품질과 운영 판단

- 인페인팅: 지정한 테이블 영역에 빨간 꽃이 생성됐다. 마스크 외부는 원본 합성으로 보존했다.
- 픽셀 검증: 마스크 경계에서 15px 이상 떨어진 보존 영역은 인페인팅 993,907픽셀, 아웃페인팅 544,644픽셀 모두 원본과 RGB 차이가 0이었다. 두 배경 제거 출력에 실제 alpha=0 픽셀이 있음을 확인했다. 수치는 `output-checks.json`에 기록했다.
- 아웃페인팅: 768×768 원본을 가운데 놓은 1024×1024 캔버스의 바깥을 채웠다. 주변 주방과 테이블은 생성됐지만 중앙 원본과 바깥 테이블의 사각 경계가 눈에 띈다. 현재 설정만으로 완성 품질이라고 볼 수 없다.
- 추가 LoRA 없이 두 작업이 실제 실행되므로 기능상 필수는 아니다. 더 좋은 아웃페인팅 품질에 LoRA가 얼마나 도움이 되는지와 그 메모리는 이번에 측정하지 않았다.
- 기존 가용량 13.08GiB보다 FLUX 전체 실행 증가량 약 18.4GiB가 크다. 단순 예산 계산으로 약 5.4GiB가 부족하며 운영 여유는 별도로 필요하다. LLM 캐시/예약량을 줄이거나 이미지 작업 동안 LLM을 내리는 방안을 검토해야 한다. 실제 동시 실행에서는 ComfyUI 오프로딩과 캐시 정책이 달라질 수 있어 OOM 여부를 확정한 결과는 아니다. 동시 실행 검증은 하지 않았다.
- 배경 제거는 FLUX를 올리지 않고 별도 단기 CPU 프로세스로 처리하는 것이 이번 실측에서 가장 가볍다. 이미지 생성은 실행 후 회수하는 방식이 메모리 확보에 유리하다.

## 기록과 재현 조건

`run_measure.py`는 명령 실행 동안 호스트를 약 100ms, GPU 프로세스를 약 1초 간격으로 샘플링한다. 표는 **관측 피크**이며 순간 최대값의 보장은 아니다. CUDA allocator 내부 최대값은 측정하지 않았다. 시간은 API 호출/프로세스 실행 및 파일 저장을 포함하며 순수 모델 추론 시간과 다르다. 각 조건 1회, 배경 제거만 프로세스당 동일 사진 2회다.

`*.summary.json`에 실행 명령과 수치, `results.json`에 비교용 요약, `requirements-measured.txt`에 배경 제거 패키지 버전을 보관했다. 첫 FLUX 측정 `flux-edit-cold`는 패키지 설치가 겹쳐 참고용이며 표에는 설치 완료 후 `flux-edit-cold-clean`을 사용했다. 실행 직전과 전체 모델 정지 기준의 증가량은 서로 다르므로 summary의 `peak_increment`와 표의 전체 FLUX 증가량을 혼동하지 말아야 한다.

LanPaint commit: `32cf848e93971da380d868936e007f5611218bee`. 실험용 노드를 기존 컨테이너에 잠시 추가했다가 제거했다. Talk 설정은 변경하지 않았다. 입력 사진, 출력 이미지와 마스크는 `private/`, 설치 환경/모델은 `downloads/`, 원시 샘플과 로그는 로컬에 보관하고 Git에서 제외한다.

원리/공식 구현 참고: [LanPaint](https://github.com/scraed/LanPaint), [rembg](https://github.com/danielgatis/rembg). 위 수치는 문서의 요구 사양이 아니라 이 장비에서 직접 측정한 값이다.

## 복구 확인

기존 모델 컨테이너 4개를 모두 재시작했다. 포트 8000/8691/8692/8693의 `/health`가 모두 200이었고, Qwen3.8 Flash Next에 1토큰 생성 요청도 200으로 완료했다. `restoration-checks.json`, `after-restore.json`에 기록했다. FLUX는 원래처럼 가중치를 아직 로딩하지 않은 API 대기 상태다.

복구 직후 전체 사용량은 약 99.00GiB, 가용량은 22.63GiB였다. 재시작은 이전의 런타임 캐시·지연 로딩 상태를 그대로 재현하지 않으므로 측정 전 108.55GiB와 다르다. 증가 원인을 각각 분리 측정하지 않았으므로 차이를 전부 KV 캐시로 단정할 수 없다. **따라서 기존 운영 상태의 13.08GiB 여유를 기준으로 한 부족량 계산과, 재시작 직후에는 더 많은 여유가 있다는 사실을 함께 고려해야 한다.** 현재 상태에서 동시 실행이 반드시 실패한다는 의미가 아니며, 실제 대화·비전·음성 사용 후의 동시 피크 검증은 별도다.

LLM 복구는 본체 가중치 로딩 약 679초 이후 MTP 초기화까지 필요했다. 매 이미지 작업마다 LLM을 내렸다 올리는 운영은 이 시작 지연을 감안해야 한다. LLM 메모리 예산을 조정하는 방안은 이번 작업에서 변경하거나 검증하지 않았다.

## 후속 확인: 사용자의 실제 대화에서 이미지 2장 생성

사용자 요청으로 `신길동 내일 날씨` 대화를 재확인했다. 메시지 1487의 재생성된 답변과 1489에서 각각 image_generate가 성공했다. 둘 다 1024×1024이며 FLUX 로그에 `/v1/images/generations` 200이 두 번 기록됐다. ComfyUI 작업 시간은 11.92초, 3.12초였다. 두 번째 요청도 생성 경로이며 마스크 편집 경로의 검증은 아니다.

LLM과 FLUX를 동시에 올려 둔 상태에서 두 작업이 순차 완료됐다. 확인 시 두 컨테이너 모두 Running, OOMKilled=false, RestartCount=0이었다. 생성 후 전체 사용량 111.70GiB, 가용량 9.93GiB, swap 사용량 1.37GiB. GPU 프로세스 기준 LLM 84.76GiB, FLUX 6.50GiB, TTS 1.27GiB, ASR 1.16GiB. 원본은 `after-user-two-images.json`에 저장했다.

이는 현재 구성에서 LLM 상주 상태의 실제 이미지 생성이 가능하다는 직접 증거다. 앞선 단독 실행 증가량을 운영 전 사용량에 단순 합산한 부족량 계산보다 이 후속 결과를 우선한다. 다만 이번 확인은 생성 **후** 스냅샷이며 두 작업 중의 전체 메모리 피크를 소급 측정한 것은 아니다. 긴 대화, 비전 입력, ASR/TTS 실제 처리와 겹친 피크 또는 여러 이미지 동시 실행까지 확인한 결과도 아니다.
