## 운영 판단

1. 메모리를 절약하기 위해 SANA 또는 Mobile-O로 바꾸는 것은 **실제 이득이 있는 선택**이다. KV 컨텍스트를 줄일 때 예상한 1~2GiB 수준보다 효과가 훨씬 컸다.
2. 1024 생성이 필요하면 이번 기존 SANA 구성은 약 8GiB를 예산으로 잡을 수 있는 출발점이다. 실제 운영 여유는 별도다.
3. 512 출력이 충분하면 Mobile-O CUDA 구성이 더 가볍다. 그러나 초기에 약 7.2GiB가 필요했고 원본 보존 편집 결과가 부족했다. iPhone의 2GB 미만과 혼동하면 안 된다.
4. 현재 FLUX가 실제 LLM 상주 상태에서 이미 생성에 성공한 점을 고려하면, 메모리만으로 즉시 교체할 필요는 없다. 원본 보존이 중요한 작업은 FLUX와 실제 배경 제거 도구를 연결하는 방향도 타당하다.
5. 이번 비교는 다른 모델을 내린 **단독 실행**이다. SANA/Mobile-O를 기존 LLM과 함께 실제 추론시킨 동시 피크는 측정하지 않았다.

공식 구현: [SANA](https://github.com/NVlabs/Sana), [Mobile-O](https://github.com/Amshaker/Mobile-O), [Mobile-O 모델](https://huggingface.co/Amshaker/Mobile-O-0.5B). 이 보고서의 메모리·시간은 위 문서의 수치가 아니라 이 장비에서 직접 얻은 값이다.

## 기존 서비스 복구

기존 LLM·ASR·TTS·FLUX 네 컨테이너를 모두 복구했다. 포트 8000/8691/8692/8693의 health가 모두 HTTP 200이었고, LLM의 1토큰 생성 요청도 정상 완료했다. SANA와 Mobile-O 실험 컨테이너는 정지 상태다. `restoration-checks.json`, `after-restore.json`에 확인 결과를 저장했다.

LLM 설정은 context_length=65,536, max_running_requests=2, mem_fraction_static=0.79로 유지했다. 단, max_total_tokens가 자동인 구성에서 **재시작 후 실제 KV 토큰 풀은 160,832로 산정됐다**. 이전 실행에서 확인한 135,360과 다르며, 수동으로 KV 설정을 변경한 것은 아니다. 재시작 전의 캐시·지연 로딩 상태도 그대로 재현되지 않는다. FLUX는 API가 준비된 대기 상태로 복구했으며 이미지 가중치를 다시 워밍하지 않았다.

Talk 이미지 설정은 enabled=true, mode=basic, 기존 FLUX endpoint/model 그대로다. 이번 작업은 메모리 검증이며 rembg/LanPaint/SANA/Mobile-O를 Talk에 연결하거나 엔진을 교체하지 않았다.
