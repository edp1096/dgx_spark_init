# 본체 가중치 유지와 작업 버퍼 반환

운영 이미지:
- FLUX: `sparktalk-flux2-paint:resident1`
- Nemotron: `sparktalk-nemotron-asr:0.6b-q8-diar2-workspace`

## FLUX

매 요청의 `unload_all_models()`를 제거했다. 생성 본체와 VAE의 로더 캐시를 유지하고, 문장 인코더도 여유가 있으면 동일 객체를 재사용한다. 작업이 끝나면 conditioning, latent, 이미지, sampler/guider 결과 캐시를 제거한 뒤 미사용 CUDA allocator와 CPU allocator 메모리를 반환한다. LoRA는 현재 그래프의 로더 캐시만 유지한다.

부가 텍스트 인코더를 처리한 뒤 시스템 가용량이 6.5GiB 미만이면 해당 인코더만 해제해 생성 작업 공간을 확보한다. 이때도 생성 본체와 VAE의 캐시는 유지한다. 항상 모든 가중치를 유지할 수 있다는 보장은 아니다.

`/v1/runtime/memory`는 문장 인코더의 재사용 상태에 따라 다음 요청의 추가 작업 예산을 반환한다. 장치에 유지되어 있으면 2.5GiB, 다시 준비해야 하면 4.5GiB다. Talk는 `max(전체 예산 - 현재 상주, 추가 작업 예산)`으로 계산한다. 이미 올라간 가중치를 다음 요청의 작업 공간으로 잘못 간주하지 않는다. 조회 실패 시 4.5GiB를 사용한다.

세트 기동 단계에서 아직 올리지 않을 부가 모델의 작업 예산을 미리 예약하지 않는다. 요청 직전에 실제 여유를 확인하고, 부족할 때만 유휴 경쟁 모델을 회수한다.

## Nemotron ASR

고정된 NeMo-Speech.cpp 소스에 `Session::release_workspace()`를 추가했다. backend compute mutex로 보호하고 CUDA 동기화 후 입력 형태별 실행 그래프와 scheduler activation pool을 해제한다. `model_tensor_container`와 가중치 버퍼는 유지한다. 전사 및 화자 API 응답을 만든 뒤 호출하며 `SPARKTALK_RELEASE_WORKSPACE=1`인 전용 HTTP 런타임에서 활성화한다.

빌드 패치: `compose_yaml/nemotron_asr/patches/release_workspace.py`. 기존 단일 HTTP worker, ASR 배치 비활성 설정을 유지한다. Talk의 길이별 전사 예산은 낮추지 않았다.

## 검증

- FLUX 생성 2회, 참조 편집, 인페인트, 아웃페인트, 물체 제거, 배경 정리, LoRA+rembg 통과. 본체/VAE 캐시 객체와 텍스트 인코더 객체의 동일성은 로그로 확인했다.
- 초기 무조건 텍스트 인코더 유지 변형은 압박 시험에서 스왑이 증가해 저메모리 성공 결과로 채택하지 않았다. 최종 구현은 여유에 따라 부가 인코더만 해제하며 별도 작업 공간을 예약한다.
- ASR 30초·10분·1시간·다시 30초의 전사/화자 구분을 모두 처리했다. 전사 텍스트와 화자 구분 JSON이 기존 결과와 동일했다.
- 1시간 전사는 111.6초, 작업 후 상주는 2.82GiB로 반환됐다. 가중치 버퍼 주소와 바이트 수가 유지되는 것을 로그로 확인했다. 짧은 요청으로 돌아와도 본체를 다시 로딩하지 않았다.
- 테스트 당시 Qwen 설정 문맥은 1,048,576이지만 실제 KV 풀은 758,656이었다. 이번 결과를 전체 1M KV 동시 사용 검증으로 취급하지 않는다. Qwen의 프로세스와 설정은 이 작업에서 변경하지 않았다.

원시 기록: `~/.cache/runtime-inspection/flux-resident/`, `~/.cache/runtime-inspection/asr-workspace/`. 압박 시험 중 스왑이 증가한 기록도 보존했다. 현재 상주량, 요청 중 피크, 기동 예상 예산은 서로 다른 값이다.

최종 Talk 연동 검증: 새 FLUX/ASR 이미지로 이미지와 음성을 교대로 두 차례 처리했다. 일반 조건 두 번째 이미지는 5.18초. 별도 압박 시험은 초기 가용 9.03GiB, 최저 6.23GiB, 추가 스왑 0, FLUX PID 1241339 유지, 본체/VAE 캐시 객체 유지. 압박 컨테이너가 OOM으로 사라진 결과가 아님을 확인했다. 이 시험 후 부가 모델을 다시 준비하고 이미지·화자 전사를 재검증했다. 기록은 `~/.cache/runtime-inspection/weights-pressure-final/` 및 `weights-resident/`에 있다.

## 실제 1M KV 복구 후 검증 (2026-09-28)

부가 서비스를 내려 Qwen을 먼저 재기동했다. `/server_info`에서 설정 문맥과 실제 KV 용량 모두 **1,048,576**, MTP steps 3을 확인했다. 이미지 생성·화자 전사 두 라운드 통과 후에도 이 값이 유지됐다. 이어진 이미지 연속 요청은 7.74초·6.18초, FLUX PID 1294392를 유지했다. Qwen PID 1261549도 유지했다. 원시 기록: `/tmp/weights-full1m-live.log`, `/tmp/weights-full1m-reuse.log`.

초기 50초 측정 구간의 최소 가용량은 8.53GiB, 스왑 증가 0이었다. 전체 시험 뒤 스왑 사용량은 약 0.44GiB에서 0.75GiB로 증가했다. 따라서 전체 시험을 제로 스왑으로 판정하지 않는다. 1M 토큰 입력 전체를 실제 prefill한 시험은 아니며, 실제 KV 할당 및 부가 작업 동작 검증이다.

일반 상태 조회에서도 HTTP 정상 여부와 함께 실제 KV 용량을 확인한다. KV가 설정 문맥보다 작으면 일시적 상태 유예 없이 부족 상태와 실제 토큰 수를 표시한다. 관련 orchestrator/server race 테스트 통과.

## 재기동 시 KV 부족 및 부가 서비스 중복 검사 수정

후속 재기동에서 SGLang 로그가 `profiled value 1038080`으로 KV 상한을 낮춘 것을 확인했다. 실행 중 캐시 용량이 줄어든 현상과 구분한다. 1M용 Compose의 `mem-fraction-static`을 0.85에서 0.86으로 조정하되, `max-total-tokens=1048576`과 MTP 설정은 유지한다. 실제 KV 검사는 계속 적용하므로 목표 이하를 정상으로 숨기지 않는다.

부가 작업 경로에서 공통 메모리 검사에 더해 적용하던 고정 4GiB 즉시 여유 검사를 제거했다. 공통 검사에 설정된 최소 여유(현재 1.5GiB)와 요청별 추가 예산은 유지한다. 가용 8GiB·즉시 여유 3.8GiB에서 불필요하게 거부하지 않는 회귀 테스트를 추가했다. 이는 CUDA 자체가 모든 상황에서 1.5GiB로 충분하다는 주장이 아니다.

실측 테스트는 라운드 전후 `/proc/vmstat`의 pswpin/pswpout 차이를 페이지 크기로 환산해 기록한다. 시스템 전체 카운터이므로 다른 프로세스 I/O와 모델별 원인 귀속은 구분한다.

수정 후 실측: 실제 KV 1,048,576 유지, 이미지·화자 전사 반복 성공. 초기 네 라운드의 시스템 스왑 쓰기는 순서대로 65,536 / 16,576,512 / 138,764,288 / 1,066,053,632바이트였다. 이후 이미지 단독 2회, 전사 단독 2회, 교대 요청 2회는 모두 스왑 쓰기 0이었다. 따라서 매 요청 무한 반복 쓰기로 관측되지는 않았지만 최초 한 번만 쓴다는 조건도 충족하지 않는다. 더 긴 음성·다른 이미지 작업의 무쓰기 보장으로 확대하지 않는다. 이미지 단독 반복은 PID 2142185 유지, 4.99초·4.43초. 최종 교대 이미지 5.32초·5.55초, 전사 포함 대기 시간 6.20초·6.44초.

원시 로그: `/tmp/qad86-workloads.log`, `/tmp/qad86-workloads-warm.log`, `/tmp/qad86-image-repeat.log`, `/tmp/qad86-asr-repeat.log`, `/tmp/qad86-final-repeat.log`. 수정 바이너리를 적용해 Talk를 다시 시작했다.


## 부가 모델 컨테이너 스왑 금지

Talk 내장 FLUX·ASR Compose와 독립 Nemotron Compose에 `mem_limit: 112g`, `memswap_limit: 112g`를 동일하게 설정했다. 이 값은 cgroup 메모리 상한으로, 112GiB 선할당이나 모델의 예상 사용량이 아니다. GPU 메모리 전체 사용량을 이 상한만으로 보호한다고 간주하지 않으며 기존 시스템 여유 및 작업 예산 검사를 유지한다. 호스트 스왑 설정은 변경하지 않았다.

실제 생성된 Qwen·FLUX·ASR cgroup에서 `memory.swap.max=0`, `memory.swap.current=0`, `oom=0`, `oom_kill=0`을 확인했다. 이미지·화자 전사 두 라운드가 통과했고 두 라운드 모두 시스템 스왑 쓰기 0이었다. 1시간 음성 전사·화자 구분은 130.24초에 성공했다. 이 시험의 시스템 전체 스왑 쓰기는 15,544,320바이트였지만 세 모델 cgroup은 모두 스왑 0·OOM 0이었다. 호스트 전체 스왑과 모델별 스왑을 혼동하지 않는다. Qwen 실제 KV는 1,048,576 유지. 시험 범위를 넘는 모든 입력의 무OOM을 보장하지 않는다.

원시 로그: `~/.cache/runtime-inspection/no-swap/`.
