# 본체 가중치 유지와 작업 버퍼 반환

2026-10-06: 기본 이미지 서비스를 Qwen Image 2.1로 교체했다. 현재 정책은 [Qwen Image 2.1 운영 문서](qwen-image21-runtime.md)를 따른다. 아래 FLUX 본체 상주·LoRA 기록은 이전 운영 검증이며 Qwen Image 2.1의 종료 정책과 구분한다.

운영 이미지:
- Qwen Image 2.1: `sparktalk-qwen-image21:nvfp4-int8-v3-lifecycle`
- 이전 FLUX: `sparktalk-flux2-paint:resident4`
- Nemotron: `sparktalk-nemotron-asr:0.6b-q5-k-diar2-workspace` (2026-10-06 Q5_K 전환; 아래 이전 검증 기록은 Q8 기준)

## FLUX

매 요청의 `unload_all_models()`를 제거했다. 생성 본체와 VAE의 로더 캐시를 유지하고, 문장 인코더도 여유가 있으면 동일 객체를 재사용한다. 작업이 끝나면 conditioning, latent, 이미지, sampler/guider 결과 캐시를 제거한 뒤 미사용 CUDA allocator와 CPU allocator 메모리를 반환한다. LoRA는 현재 그래프의 로더 캐시만 유지한다.

부가 텍스트 인코더를 처리한 뒤 시스템 가용량이 6.5GiB 미만이면 해당 인코더만 해제해 생성 작업 공간을 확보한다. 이때도 생성 본체와 VAE의 캐시는 유지한다. 항상 모든 가중치를 유지할 수 있다는 보장은 아니다.

`/v1/runtime/memory`는 문장 인코더의 재사용 상태에 따라 다음 요청의 추가 작업 예산을 반환한다. 장치에 유지되어 있으면 2.5GiB, 다시 준비해야 하면 4.5GiB다. Talk는 `max(전체 예산 - 현재 상주, 추가 작업 예산)`으로 계산한다. 이미 올라간 가중치를 다음 요청의 작업 공간으로 잘못 간주하지 않는다. 조회 실패 시 4.5GiB를 사용한다.

세트 기동 단계에서 아직 올리지 않을 부가 모델의 작업 예산을 미리 예약하지 않는다. 요청 직전에 실제 여유를 확인하고, 부족할 때만 유휴 경쟁 모델을 회수한다.

## Nemotron ASR

고정된 NeMo-Speech.cpp 소스에 `Session::release_workspace()`를 추가했다. backend compute mutex로 보호하고 CUDA 동기화 후 입력 형태별 실행 그래프와 scheduler activation pool을 해제한다. `model_tensor_container`와 가중치 버퍼는 유지한다. 전사 및 화자 API 응답을 만든 뒤 호출하며 `SPARKTALK_RELEASE_WORKSPACE=1`인 전용 HTTP 런타임에서 활성화한다.

빌드 패치: `compose_yaml/nemotron_asr/patches/release_workspace.py`. 기존 단일 HTTP worker, ASR 배치 비활성 설정을 유지한다. Talk의 길이별 전사 예산은 낮추지 않았다.

## 검증

- FLUX 생성 2회, 참조 편집, 인페인트, 아웃페인트, 물체 제거, 배경 정리, LoRA+rembg 통과. 본체/VAE 캐시 객체와 텍스트 인코더 객체의 동일성은 로그로 확인했다.
- 초기 무조건 텍스트 인코더 유지 변형은 압박 시험에서 스왑이 증가해 저메모리 성공 결과로 채택하지 않았다. 최종 구현은 여유에 따라 부가 인코더만 해제하며 별도 작업 공간을 예약한다.
- ASR 30초·10분·1시간·다시 30초의 전사/화자 구분을 모두 처리했다. 전사 텍스트와 화자 구분 JSON이 기존 결과와 동일했다.
- 1시간 전사는 111.6초, 작업 후 상주는 2.82GiB로 반환됐다. 가중치 버퍼 주소와 바이트 수가 유지되는 것을 로그로 확인했다. 짧은 요청으로 돌아와도 본체를 다시 로딩하지 않았다.
- 테스트 당시 Qwen 설정 문맥은 1,048,576이지만 실제 KV 풀은 758,656이었다. 이번 결과를 전체 1M KV 동시 사용 검증으로 취급하지 않는다. Qwen의 프로세스와 설정은 이 작업에서 변경하지 않았다.

원시 기록: `~/.cache/runtime-inspection/flux-resident/`, `~/.cache/runtime-inspection/asr-workspace/`. 압박 시험 중 스왑이 증가한 기록도 보존했다. 현재 상주량, 요청 중 피크, 기동 예상 예산은 서로 다른 값이다.

최종 Talk 연동 검증: 새 FLUX/ASR 이미지로 이미지와 음성을 교대로 두 차례 처리했다. 일반 조건 두 번째 이미지는 5.18초. 별도 압박 시험은 초기 가용 9.03GiB, 최저 6.23GiB, 추가 스왑 0, FLUX PID 1241339 유지, 본체/VAE 캐시 객체 유지. 압박 컨테이너가 OOM으로 사라진 결과가 아님을 확인했다. 이 시험 후 부가 모델을 다시 준비하고 이미지·화자 전사를 재검증했다. 기록은 `~/.cache/runtime-inspection/weights-pressure-final/` 및 `weights-resident/`에 있다.

## 실제 1M KV 복구 후 검증 (2026-09-28)

부가 서비스를 내려 Qwen을 먼저 재기동했다. `/server_info`에서 설정 문맥과 실제 KV 용량 모두 **1,048,576**, MTP steps 3을 확인했다. 이미지 생성·화자 전사 두 라운드 통과 후에도 이 값이 유지됐다. 이어진 이미지 연속 요청은 7.74초·6.18초, FLUX PID 1294392를 유지했다. Qwen PID 1261549도 유지했다. 원시 기록: `/tmp/weights-full1m-live.log`, `/tmp/weights-full1m-reuse.log`.

초기 50초 측정 구간의 최소 가용량은 8.53GiB, 스왑 증가 0이었다. 전체 시험 뒤 스왑 사용량은 약 0.44GiB에서 0.75GiB로 증가했다. 따라서 전체 시험을 제로 스왑으로 판정하지 않는다. 1M 토큰 입력 전체를 실제 prefill한 시험은 아니며, 실제 KV 할당 및 부가 작업 동작 검증이다.

일반 상태 조회에서도 HTTP 정상 여부와 함께 실제 KV 용량을 확인한다. KV가 설정 문맥보다 작으면 일시적 상태 유예 없이 부족 상태와 실제 토큰 수를 표시한다. 관련 orchestrator/server race 테스트 통과.

## 재기동 시 KV 부족 및 부가 서비스 중복 검사 수정

후속 재기동에서 SGLang 로그가 `profiled value 1038080`으로 KV 상한을 낮춘 것을 확인했다. 실행 중 캐시 용량이 줄어든 현상과 구분한다. 1M용 Compose의 `mem-fraction-static`을 0.85에서 0.86으로 조정하되, `max-total-tokens=1048576`과 MTP 설정은 유지한다. 실제 KV 검사는 계속 적용하므로 목표 이하를 정상으로 숨기지 않는다.

부가 작업 경로에서 공통 메모리 검사에 더해 적용하던 고정 4GiB 즉시 여유 검사를 제거했다. 공통 검사에 설정된 최소 여유(현재 1.5GiB)와 요청별 추가 예산은 유지한다. 가용 8GiB·즉시 여유 3.8GiB에서 불필요하게 거부하지 않는 회귀 테스트를 추가했다. 이는 CUDA 자체가 모든 상황에서 1.5GiB로 충분하다는 주장이 아니다.

실측 테스트는 라운드 전후 `/proc/vmstat`의 pswpin/pswpout 차이를 페이지 크기로 환산해 기록한다. 시스템 전체 카운터이므로 다른 프로세스 I/O와 모델별 원인 귀속은 구분한다.

수정 후 실측: 실제 KV 1,048,576 유지, 이미지·화자 전사 반복 성공. 초기 네 라운드의 시스템 스왑 쓰기는 순서대로 65,536 / 16,576,512 / 138,764,288 / 1,066,053,632바이트였다. 이후 이미지 단독 2회, 전사 단독 2회, 교대 요청 2회는 모두 스왑 쓰기 0이었다. 따라서 매 요청 무한 반복 쓰기로 관측되지는 않았지만 최초 한 번만 쓴다는 조건도 충족하지 않는다. 더 긴 음성·다른 이미지 작업의 무쓰기 보장으로 확대하지 않는다. 이미지 단독 반복은 PID 2142185 유지, 4.99초·4.43초. 최종 교대 이미지 5.32초·5.55초, 전사 포함 대기 시간 6.20초·6.44초.

원시 로그: `/tmp/qad86-workloads.log`, `/tmp/qad86-workloads-warm.log`, `/tmp/qad86-image-repeat.log`, `/tmp/qad86-asr-repeat.log`, `/tmp/qad86-final-repeat.log`. 수정 바이너리를 적용해 Talk를 다시 시작했다.


## 부가 모델 컨테이너 스왑 금지

Talk 내장 FLUX·ASR Compose와 독립 Nemotron Compose에 `mem_limit: 112g`, `memswap_limit: 112g`를 동일하게 설정했다. 이 값은 cgroup 메모리 상한으로, 112GiB 선할당이나 모델의 예상 사용량이 아니다. GPU 메모리 전체 사용량을 이 상한만으로 보호한다고 간주하지 않으며 기존 시스템 여유 및 작업 예산 검사를 유지한다. 호스트 스왑 설정은 변경하지 않았다.

실제 생성된 Qwen·FLUX·ASR cgroup에서 `memory.swap.max=0`, `memory.swap.current=0`, `oom=0`, `oom_kill=0`을 확인했다. 이미지·화자 전사 두 라운드가 통과했고 두 라운드 모두 시스템 스왑 쓰기 0이었다. 1시간 음성 전사·화자 구분은 130.24초에 성공했다. 이 시험의 시스템 전체 스왑 쓰기는 15,544,320바이트였지만 세 모델 cgroup은 모두 스왑 0·OOM 0이었다. 호스트 전체 스왑과 모델별 스왑을 혼동하지 않는다. Qwen 실제 KV는 1,048,576 유지. 시험 범위를 넘는 모든 입력의 무OOM을 보장하지 않는다.

원시 로그: `~/.cache/runtime-inspection/no-swap/`.

## 2026-09-30 부품별 회수와 Extra 요청 관리

- QAD 세트 시작 시 Qwen 준비 후 Klein 본체·VAE를 사전 적재한다. Dynamic 본체의 페이지가 VAE 작업 중 회수되는 문제가 실측에서 확인돼 본체만 upstream static loader와 full load를 사용한다. NVFP4 형식은 유지한다. 실제 적재량을 검사하고, 부족할 때만 인코더 없는 256px·1단계 준비 그래프를 시도한다. 이미 본체가 준비됐으면 LoRA view를 포함해 재사용하고 준비 연산을 반복하지 않는다. 요청 시에는 본체 적재 뒤 실제 여유를 다시 측정해 인코더·샘플링 작업을 허용한다.
- 이미지 본체는 전용 로더 객체로 재사용하고 Comfy 자동 회수에서도 같은 본체와 LoRA view를 보호한다. 일반 메모리 압박이나 다른 서비스 실패를 이유로 Klein 컨테이너를 중지하지 않는다. 명시적인 세트/서비스 중지와 언어 모델 재기동 전 준비는 별도다.
- 회수 순서는 유휴 로컬 Extra, Klein 선택 인코더·LoRA/결과 캐시, 유휴 ASR이다. 한 대상 회수 후 실제 여유를 재검사한다. Dynamic LoRA의 일반 `unpatch_model()`은 공유 본체 vbar까지 해제하므로 호출하지 않는다. 준비된 adapter tensor와 캐시를 제거하고 다음 managed load의 정상 patch UUID 경로로 전환한다. Static LoRA는 CUDA 장치에서 원래 가중치를 복원하고 본체를 CPU로 옮기지 않는다. LoRA 사용 전후 같은 시드의 일반 생성 결과가 픽셀 단위로 동일함을 확인했다.
- Documents, 채팅 Collector, 지식 가져오기와 백그라운드 수집도 완료까지 작업 lease를 보유한다. 지원 서비스의 `busy`/`active` 응답도 확인한다. 작업을 허용하기 전 실패했다고 진행 중인 다른 요청을 취소하지 않는다. 원격/외부 소유 Extra와 SSH는 자동 회수하지 않는다.
- 이미지 취소는 해당 API 요청의 prompt ID와 CPU rembg worker를 대상으로 하고 완료를 확인한다. 전체 Comfy 대기열을 비우거나 Klein 컨테이너를 종료하지 않는다. 취소가 확인되지 않으면 실패를 알리고 본체를 유지한다.
- 실제 점유·추가 workspace·예상 예산을 구분하며, 보호된 이미지 점유와 다음 음성 작업의 필요량을 함께 예상 예산에 반영한다. 상태 조회는 적재·회수를 수행하지 않는다.

포트 없는 Go lifecycle 테스트 6건, Python Comfy lifecycle/API 모의 테스트 8건과 선택한 메모리/카탈로그 회귀 검사, 웹 단위 검사·빌드, 내장 자산 동기화 검사를 통과했다. 전체 Go 서버 테스트는 로컬 listen 권한 거부로 실행되지 못했다. 이 결과는 실제 NVFP4 수치 동일성, GPU 상주 유지, 작업별 최대 메모리나 제로 스왑을 입증한 결과가 아니다.

## 2026-09-30 참조 이미지와 여러 단계 편집 검증

- 원본 참조를 최대 4장까지 순서대로 전달한다. `identity_edit`에서는 편집 대상이 첫 번째이고 원본 참조를 뒤에 붙인다. 생성 결과의 ID는 같은 턴의 다음 편집에서 바로 사용 가능하다.
- 사진의 ID·출처 표시는 시각 입력 바로 앞에 붙인다. 원본 대신 과거 생성물만 보내거나 참조를 텍스트 생성에 누락하는 요청은 거절한다. 실제 전송한 입력 목록을 결과 및 웹 UI에 남긴다. 이 검사는 잘못된 인물 설명까지 판별하는 의미 검증이 아니다.
- 참조 전처리는 중앙 잘라내기 대신 전체 구도를 유지하고, 여러 참조가 하나의 픽셀 예산을 나눠 쓴다. 원본 얼굴을 이용한 장면 수정은 전체 참조 편집이며 마스크 밖 픽셀 보존이나 정확한 얼굴 복사를 보장하지 않는다.
- 실제 Qwen으로 원본 두 장의 순서, 각각의 편집 대상 ID, 중간 장면에 원본 두 장을 다시 붙이는 호출을 검증했다. 누락한 필수 prompt는 서버가 거절한 뒤 모델이 수정했다. 모델이 항상 첫 호출을 정확히 만드는 것은 아니다.
- 실제 Klein에서 원본 두 장의 장면 생성, 각 사진 리터칭, 생성 장면+원본 두 장의 2차 편집을 완료했다. 일반 생성·인페인트·아웃페인트·LoRA 사용 후 재생성도 통과했다. 인페인트 마스크 밖 픽셀과 아웃페인트 내부 픽셀 보존을 확인했다.

## 참조 생성 후 BFS 실행 계획 추적

paint 모드 `reference_generate`는 `head_targets`를 명시한다. 인물·캐릭터 머리 참조는 원본 ID와 장면 속 대상을 지정하고, 사물·배경·스타일 참조는 빈 배열을 사용한다. 필드 누락은 생성 전에 거부한다. Talk는 선언된 계획을 추적하며, 모델이 중간에 완료 답변을 내면 남은 BFS 호출을 정상 도구 실행 경로로 처리한다. BFS 도구를 모델이 직접 선택해도 계획의 대상/원본/최신 장면 연결을 사용한다. 장면 재생성은 미완료 대상을 유지해야 한다. 실패한 단계는 한 번 기록하고 다음 단계로 넘어가며 모두 종료하면 완료로 포장하지 않고 실패를 표시한다. 실행 라운드 한도도 유지한다.

실제 Qwen 전체 루프 검증은 장면 생성 1회→BFS 2회, 출력 3장으로 성공했다. Talk `BFS 자동 보정 검증` 대화(`bfs-plan-check-1790772309252079992`)에 원본·결과·호출 기록을 저장했다. 결과 검토상 신문과 손의 관계 및 때리는 동작은 여전히 어색하고, 전체 장면 보정은 다른 인물의 얼굴에도 영향을 줬다. 실행 계획 완료를 시각적 품질 보장으로 해석하지 않는다.

초기 5GiB 작업 예산은 당시 가용 6.3GiB에서 실행을 거부했다. 이전 BFS 측정 구간 가용량 감소 약 1.43GiB 및 후속 실측에 따라 4.5GiB 작업 예산과 최소 여유 1.5GiB로 검증했다. 전체 루프 측정 구간의 최소 시스템 가용량은 약 4.63GiB, FLUX 컨테이너 스왑/OOM은 0이다. 시스템 스왑 쓰기는 520,028,160바이트 관측됐으므로 무스왑 동작으로 보고하지 않는다. 기록: `/tmp/sparktalk-head-plan-memory.jsonl`, `/tmp/sparktalk-head-plan-live-final.log`.


## 이미지 제작의 4단계 작업 절차

`identity-image-production` 내장 절차를 입력 도구의 스킬·작업 절차에서 선택할 수 있다. 순서는 스타일·구도 생성 → 구도·동작 검토 → 인물별 얼굴 보정 → 최종 결과 검토다. 일반 `image-production` 절차는 유지한다.

- 장면 단계는 보정 계획을 선언하지만 BFS를 실행하지 않는다.
- 구도 검토는 생성된 실제 이미지 읽기 근거가 필요하다. 실패하면 장면 생성으로 한 번만 돌아간다.
- 얼굴 보정 단계는 선언된 BFS만 실행하며 새 구도·스타일 생성은 거부한다.
- 최종 검토는 보정 전 장면과 최종 이미지 모두를 읽어야 한다. 이 단계에서 이미지를 다시 생성할 수 없다. 품질 판단은 모델의 시각적 검토이며 프로그램이 닮음이나 동작을 보증하는 것은 아니다.
- 중간 이미지와 보정 계획을 다음 단계로 전달하고, 재개 시 성공한 도구 기록에서 복원한다. 이미 끝난 머리 교체는 다시 실행하지 않는다.
- 이미지 단계의 증거는 모델이 복사한 호출 ID 대신 서버에 기록된 실제 성공 호출에서 확인한다. 도구 종류·읽은 이미지 ID 검사는 유지한다.

단계 순서, 미완료 보정 생략 차단, 이전 이미지와 최종 이미지 읽기 누락 차단, 부분 보정 복원, 이미지 기능의 절차 선택 가능 여부를 테스트했다. 모바일 절차 구성 화면 및 기존 절차의 중단·재개 E2E도 통과했다.

실제 Qwen·FLUX 실행은 네 단계 모두 진행됐다. 생성 1회, 구도 이미지 읽기, BFS 2회, 보정 전후·원본 이미지 읽기를 확인했다. Talk의 `이미지 단계별 제작 검증 · 22:23` 대화(`bfs-plan-check-1790774613628324308`)에서 단계 기록과 결과를 볼 수 있다. 소요 약 240초. 절차의 통과는 모델의 시각적 판정과 실제 도구 기록을 의미하며 원본 얼굴과 완전히 동일하다는 보증은 아니다.


## 같은 인물의 여러 참조 사진

paint `reference_generate`에 `reference_groups`를 추가했다. 인물별 후보 사진 ID, 장면 생성용 선택, 머리 보정용 선택, 대상 위치, 선택 이유를 명시한다. 세 장씩 두 인물이면 여섯 후보를 보존하되 장면 생성에는 선택한 두 장, BFS에는 각 인물의 선택된 머리 사진 한 장씩을 전달한다. Qwen의 후보 검토와 Klein/BFS의 실제 입력을 구분한다. 여러 원본을 BFS가 동시에 융합하는 기능은 아니다.

다른 인물의 사진 선택, 묶음 간 중복 ID, 존재하지 않는 미선택 후보도 거부한다. 작업 절차 재개 시 후보 묶음과 서로 다른 생성용·보정용 선택을 복원한다. 도구 결과 화면에 인물별 후보와 선택 사진을 표시한다. 한 메시지 첨부 상한 6개와 실제 생성 호출의 선택 이미지 상한 4개는 별개이며, 오류 문구에서 이를 모델 자체의 한계처럼 표현하지 않는다.

6개 후보→2개 생성 입력, 다른 보정 사진 선택, 교차 인물 선택 거부, 누락 후보 거부, 작업 재개 복원 및 모바일 후보 표시 테스트를 통과했다.

실제 Qwen 전체 실행에서 등소평 3장·시진핑 3장을 두 묶음으로 선언하고, 장면 생성 1회→BFS 2회를 약 120초에 완료했다. 기존 요청의 저장된 첨부는 5장이므로 같은 대화의 시진핑 원본 1장을 보완해 검증했으며, 이 내용을 검증 요청 본문에 명시했다. 결과는 Talk 대화 `bfs-plan-check-1790776303896088526`에 원본·그룹 선택 근거·출력 3장과 함께 저장했다. 최종 이미지는 직접 확인했으며, 실행 완료와 원본 얼굴의 완전한 재현은 구분한다.


## resident4 전체 메모리 재측정 — 2026-10-01

Qwen을 유지하고 유휴 FLUX를 재기동해 1024 작업 10회를 순차 실행했다.
