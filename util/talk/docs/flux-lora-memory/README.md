# FLUX / LoRA 메모리 실측 — 2026-09-13

대상은 `sparktalk-flux2-paint:trial3`의 FLUX.2 Klein 4B NVFP4,
LanPaint 인페인팅 발췌 모듈, fal LoRA 3종, CPU rembg U²-Net이다.
컨테이너의 API·LoRA 준비·rembg·시작 스크립트가 저장소 원본과 일치함을 확인했다.

## 측정 방식

- LLM·ASR·TTS는 정지된 상태였다. 기존 Extra 4개만 그대로 두고 FLUX를 실행했다.
- `/proc/meminfo`의 `MemTotal - MemAvailable`을 50ms 간격으로 관측했다.
  GPU 프로세스 메모리는 작업 후 별도 기록했으며 호스트 수치에 더하지 않았다.
- 개별 작업은 매번 컨테이너를 재시작했다. 표의 추가량은 **API 준비 후 작업 직전 대비**다.
  API 프로세스 자체의 메모리까지 포함한 기동 예산으로 그대로 사용할 수 없다.
- 1024×1024, seed 42, batch 1. FLUX로 생성한 컵 사진을 공통 입력으로 사용했다.
  아웃페인트는 768×768 입력에 사방 128px를 추가했다. 물체 제거·인페인트는 같은 사각 마스크다.
- 연속 시험은 재시작 없이 참조 편집 → (아웃페인트 → 물체 제거 → 배경 정리) × 3 → 참조 편집이다.
  매 요청의 입력 파일명은 새로 만들어진다. 실제 샘플러 실행을 로그와 실행 시간으로 확인했다.
- 출력 PNG 크기·디코딩, rembg alpha 범위를 검사했다. 단일 입력의 관측 피크이며 모든 입력의 최대값을 보장하지 않는다.

## 기존 설정의 개별 결과

| 작업 | 작업 직전 대비 피크 증가 (GiB) | 요청 시간 (초) |
|---|---:|---:|
| 일반 생성 | 16.88 | 7.93 |
| 참조 편집, LoRA 없음 | 16.92 | 9.36 |
| outpaint LoRA | 16.98 | 11.23 |
| object-remove LoRA | 16.74 | 11.52 |
| background-remove LoRA | 17.01 | 11.36 |
| LanPaint 인페인트 | 16.86 | 14.26 |
| rembg U²-Net | 0.53 | 1.62 |

이 값은 **각 LoRA 파일 자체의 메모리 크기가 아니라 FLUX를 포함한 작업 전체 증가량**이다.
LoRA 파일은 각각 약 73MiB이며 한 작업에는 하나만 적용한다.
다른 이미지 처리 경로와 기준 시점의 변동 때문에 이 표의 차이를 LoRA 자체의 정확한 할당량으로 해석하지 않는다.

연속 전환 전 참조 편집 후 전체 사용량은 19.73GiB, 9번 전환하고 참조 편집으로
돌아온 후에는 19.55GiB였다. 반복 횟수에 따른 메모리 누적 증가는 관측되지 않았다.
rembg 출력은 alpha 0~255의 RGBA PNG였고, CPU 작업 프로세스는 요청 후 종료됐다.

## 캐시 구현 확인

기본값은 ComfyUI RAM pressure cache다. 활성 캐시와 비활성 캐시의 반환 기준이 다르다.
현재 기본 비활성 기준은 시스템 RAM 100%(최대 128GiB)이며, 실행 중 이전 워크플로의
ModelPatcher를 먼저 제거하도록 되어 있다. 따라서 “RAM 여유가 많으면 이전 LoRA가
계속 누적된다”고 단정할 수 없다. 실제 반복 시험에서도 누적이 없었다.
LoRA 로더는 파일이 바뀌면 이전 `loaded_lora` 참조를 해제한다. 이것이 즉각적인
OS 메모리 반환을 보장하는 것은 아니지만, 별도 강제 해제 코드를 넣어야 할 근거도 얻지 못했다.

## 재현

`measure.py`는 실행 중인 FLUX 컨테이너에 요청하고 개별 조건마다 재시작한다.
측정 전 다른 GPU 작업이 없는지 확인해야 한다. 출력 경로는 `FLUX_BENCH_OUTPUT`으로
지정할 수 있으며 기본값은 `/tmp/flux-lora-memory-20260913`이다.
`variants.py`는 이 결과의 입력 사진과 보관한 `base_start.original.sh`를 사용해
캐시 설정 및 pinned-memory 비활성화 조건을 비교한다. 컨테이너의 시작 스크립트를
실험용으로 바꾸므로 시험 종료 후 채택한 설정 또는 원본을 복구해야 한다.
원시 50ms 샘플과 출력 PNG는 해당 `/tmp` 경로에 보관한다.

## 채택한 변경: pinned-memory 비활성화

`--cache-classic`만 적용한 시험은 피크 절감 효과가 없어서 채택하지 않았다.
기본 RAM pressure cache는 유지하고 **`--disable-pinned-memory`만 추가**했다.
GB10 통합 메모리에서 고정 staging 버퍼를 줄인 것이며 모델 가중치·정밀도·LoRA 강도·
샘플러·단계·프롬프트는 변경하지 않았다. 이미지 태그는 `sparktalk-flux2-paint:trial4`다.

| 작업 | 이전 추가 피크 (GiB) | 변경 후 추가 피크 (GiB) | 이전 → 변경 후 시간 (초) |
|---|---:|---:|---:|
| 참조 편집 | 16.92 | 10.90 | 9.36 → 9.66 |
| outpaint LoRA | 16.98 | 10.84 | 11.23 → 9.79 |
| object-remove LoRA | 16.74 | 10.66 | 11.52 → 10.07 |
| background-remove LoRA | 17.01 | 10.75 | 11.36 → 9.88 |
| LanPaint | 16.86 | 10.76 | 14.26 → 12.73 |
| 배경 정리 LoRA → rembg | 미측정 | 10.85 | 10.95 |

모두 프로세스를 재시작한 뒤의 첫 요청이다. 변경 후 약 6GiB 감소했다.
같은 입력·seed의 참조 편집, LoRA 3종, LanPaint 출력은 변경 전과 픽셀 단위로
동일했다. `pixel-checks.json`에 개별 비교 결과를 보존했다. LoRA→rembg 출력도
alpha 0~255의 RGBA PNG였다. 시간은 단회 측정이므로 속도 향상을 일반화하지 않는다.

변경 후 9번 연속 LoRA 교체도 별도 실행했다. 기존과 마찬가지로 누적 증가가 없었다.
따라서 별도 LoRA 강제 해제 코드와 전체 모델을 매번 내리는 처리는 추가하지 않았다.

API 대기 자체의 사용량과 미측정 입력의 여유를 더해 **FLUX 카탈로그 예산을 13GiB**로
설정한다. 10.9GiB를 그대로 기동 예산으로 사용하지 않는다. Qwen 세트의 신규 예상량은
96 + 13 + 1.3 + 1.2 = **111.5GiB**이며, 117.7GiB 가용일 때 최소 여유 4GiB 검사를 통과한다.
이 예산은 trial4에만 대응한다. 기존 trial3에 예상치만 낮춰 적용하면 안 된다.

요약 수치는 `results.json`, 원시 샘플·출력은 `/tmp/flux-lora-memory-20260913`에 있다.
배포 이미지 빌드는 개별/연속 측정이 끝난 뒤 수행했다.

최종 배포 이미지 trial4로 ASR·TTS를 유지한 채 FLUX 정지 → API 시작 → 첫 LanPaint
작업을 측정했다. API 자체 증가는 1.00GiB, 정지 상태부터의 전체 추가 피크는
**11.86GiB**였다(`total-footprint.json`). 이에 약 1.14GiB 여유를 더해 13GiB로 정했다.
임시 14GiB 예산은 첫 검사는 통과했으나 주변 모델이 올라온 뒤의 두 번째 검사에서
3.3GiB만 남는 것으로 추정되어 차단됐다. 실제 사용량을 확인한 후 예산을 조정했다.
최소 확보 메모리 4GiB와 검사 로직은 그대로 유지한다.

메모리 절감은 `MemAvailable` 기준이다. pinned 메모리를 끄면 파일 캐시 등
회수 가능한 페이지가 늘 수 있으므로 `MemFree`가 같은 크기로 증가한다는 의미는 아니다.

`total-footprint.py`는 API 시작까지 포함한 전체 증가량을 측정한다.
`integration.py`는 Talk에서 Qwen 세트 시작 요청을 보낸 뒤 기동 상태를 기다리고
텍스트 응답과 이미지 5개 경로를 확인한다. 둘 다 모델 상태를 변경하거나 생성 요청을 보낸다.

## Talk 세트 기동·상주 조합 검증

최종 trial4 / 13GiB 설정을 실행 중인 Talk와 기본 카탈로그에 반영했다.
`POST /api/runtime/bundles/flash-next/start`로 처음과 LLM 직전의 두 메모리 검사를
통과했고, Qwen 체크포인트·MTP·CUDA Graph 초기화가 완료됐다. 실제 텍스트 질의
`7 + 8`의 응답은 `15`였다. Qwen의 정밀도·문맥·KV 설정은 변경하지 않았다.

Qwen·ASR·TTS·Extra 상주 상태에서 아웃페인트, 물체 제거, 배경 정리, LanPaint,
배경 정리 LoRA→rembg 5개 요청 모두 1024 PNG 생성에 성공했다.
호스트 50ms 샘플 기준 최소 가용량은 **10.44GiB**, 종료 후 약 **13.28GiB**였다.
최소 확보 설정 4GiB보다 여유가 있었다. 네 모델 컨테이너 모두 Running,
OOMKilled=false, RestartCount=0을 확인했고 기동한 상태로 두었다.

swap은 기동 전 0.30GiB에서 전체 구간 최대 1.49GiB, 종료 시 1.47GiB였다.
이미지 요청 직전에는 이미 1.41GiB였으며 이미지 구간의 추가 증가는 약 0.08GiB였다.
따라서 이 시험을 swap 증가가 전혀 없는 구성으로 해석하지 않는다.
음성의 실제 처리·장문 생성·이미지 요청을 동시에 겹치는 최대 부하는 이번 범위에 포함하지 않았다.

Go orchestrator/config/server 테스트와 Docker 이미지 빌드가 통과했다.
수치와 컨테이너 상태는 `integration-summary.json`에 보존했다.
