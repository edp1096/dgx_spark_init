# 반복 대화의 입력 처리 지연 개선

이 문서의 수치는 512토큰 입력 묶음에서 측정한 기록이다. 이후 캐시 없는
첫 입력의 처리도 개선했다. 현재 기본값과 별도 측정은
[DeepSeek 입력 처리 개선 기록](../../../compose_yaml/ds41f_vllm/docs/PREFILL_BATCHING.md)을 참고한다.

DeepSeek V4.1 Flash TP2에서 실제 SparkTalk 입력 약 6,200토큰을 매번 새로
처리하면 첫 토큰까지 약 1분이 걸렸다. 동일한 입력을 재사용할 때는 1초
안팎이었다. TTFT는 요청마다 측정하며, 이 변경은 반복 입력의 재처리를 줄인다.
새 입력에 대한 SSD expert 읽기와 연산 자체를 빠르게 만든 변경은 아니다.

## 구현

기존에는 사용자 지정 시스템 지침 뒤에 회상 기억·대화 체크포인트를 넣고,
그 뒤에 도구 안내와 도구 정의를 배치했다. 앞쪽의 기억이 달라지면 뒤의
동일한 도구 문맥까지 캐시에서 재사용할 수 없었다.

이제 고정 지침과 도구 안내는 시스템 메시지에 유지하고, 회상 자료는 마지막
사용자 메시지 앞의 `<sparktalk_context>` JSON 블록에 넣는다. 자료를 해석하는
정책은 고정 시스템 지침으로 남긴다. 선호 기억의 기존 우선순위와 현재 사용자의
명시적 수정 우선권도 유지한다. 신뢰할 수 있는 워크플로 시스템 지침은 이동하지
않으며, 내부 `ReferenceContext` 표시로 회상 자료만 구분한다.

원본 대화와 첨부 파일은 수정하지 않는다. 이미지 등 복합 입력에는 별도의
텍스트 부분을 앞에 추가한다. JSON 인코딩은 자료 안의 태그를 이스케이프한다.
문맥 토큰 예산 추정과 실제 모델 요청에 같은 배치를 적용한다.

고정 vLLM의 sliding-window 캐시 보존 간격도 0에서 128토큰으로 변경했다.
0은 일부 의미 있는 경계만 보존하고, 양수는 주기적 경계를 추가로 보존한다.
해당 의미는 설치된 코드와 [공식 옵션 설명](https://docs.vllm.ai/en/stable/cli/serve/#--prefix-cache-retention-interval)에서 확인했다.
레시피의 `DSV41_PREFIX_CACHE_INTERVAL`은 양쪽 rank에 전달된다. 기본값은 128이고
0으로 기존 보존 정책을 재현할 수 있다. 이 옵션의 지원 여부는 엔진 버전에 따라
달라지므로 다른 서빙 엔진에 자동으로 추가하지 않는다.

모델 가중치, 정밀도, expert 슬롯 수, DSpark5, 65,536토큰 문맥, 8,192토큰 출력
예산은 유지한다. KV 할당량도 rank당 2 GiB다. 더 많은 재사용 경계를 기존 KV
풀에 보존하므로 다른 요청과 캐시 공간을 공유하며, 영구 보존을 보장하지 않는다.

## 측정 방법

실제 SparkTalk 설정과 도구 레지스트리로 만든 요청 두 개를 비교했다.
테스트용 DB 복사본에서 선호 기억의 표식만 `cobalt731`에서 `amber962`로
바꿨으며, 질문은 동일하게 유지했다. 사용자 DB에는 해당 기억을 쓰지 않았다.
변경 전후 각각 별도의 `cache_salt`를 써서 기존 KV 캐시의 영향을 분리하고,
A → B → B 재요청 순서로 실행했다. 답변은 바뀐 표식을 정확히 반환해야 한다.

입력 처리를 비교하는 이 검사는 reasoning을 끄고 출력 상한을 32토큰으로
고정한다. 사용자 앱의 reasoning 설정이나 8,192토큰 출력 예산을 바꾸지는 않는다.
기억·지침·도구의 내용을 줄이지 않았으며, 새 포장으로 입력은 6,226에서
6,282토큰으로 56토큰 증가했다. A/B의 동일한 앞부분은 856에서 6,252토큰으로
늘었다. 원본 요청에는 비공개 설정이 포함되므로 저장소에는 수치와 검증 결과만
남긴다.

측정 파일은 `compose_yaml/ds41f_vllm/results/prefix-layout-*.json`에 있다.

2026-09-12 실측 결과(큐 대기를 포함한 서버 TTFT):

| 요청 | 기존 배치·보존 간격 0 | 새 배치·보존 간격 128 | 캐시 재사용 토큰: 기존 → 새 배치 |
| --- | ---: | ---: | ---: |
| 첫 표식 A | 56.95초 | 69.44초 | 0 → 0 |
| 기억을 B로 변경 | 57.14초 | 0.90초 | 0 → 6,144 |
| B 그대로 재요청 | 0.59초 | 0.74초 | 6,144 → 6,144 |

바뀐 기억을 사용하는 요청의 TTFT가 이 비교에서 98.4% 감소했다. 각 조건은
A/B/B 한 묶음이며 전체 6개 답변의 표식이 정확했다. 새 배치의 첫 요청은
엔진 재기동 직후였고 추론 중 JIT 경고도 있었다. 첫 요청끼리의 시간 차이를
순수 입력 처리 성능의 회귀율이나 개선율로 해석할 수는 없다. 두 변경의 결합
효과를 측정했으며 각 변경의 독립 효과나 다양한 실사용 요청의 평균은 아니다.

단위 검사에서는 회상 내용 변경·없음/있음 전환, 신뢰된 시스템 지침 유지,
이미지 첨부 보존, 원본 이력 불변과 JSON 경계를 확인했다. `go test ./...`와
릴리스 바이너리 빌드를 통과했다. 첫 전체 검사에서 기존 지식 발행 인덱스
검사가 한 번 실패했으나 해당 검사 5회 재실행과 전체 재실행은 통과했다.

## 실행 중인 SparkTalk 확인

새 바이너리를 실제 앱에 적용한 뒤 `tools/check_sparktalk_prefix.py`로 두 번의
연속 대화를 보냈다. 실제 도구 목록, reasoning `max`, 문맥 65,536과 출력
예산 8,192를 유지했다. 첫 질문은 표식 `cobalt731`, 다음 질문은 이를
`amber962`로 명시적으로 수정한다. 두 답변 모두 정확했고 오류 없이 완료됐다.

| 항목 | 첫 대화 | 바로 이어 보낸 두 번째 대화 |
| --- | ---: | ---: |
| 입력 / 캐시 토큰 | 6,333 / 0 | 6,362 / 6,144 |
| 서버 ttft | 60.61초 | 8.53초 |
| 첫 생성 이벤트 수신 | 60.64초 | 9.04초 |
| 답변 완료 | 71.03초 | 15.24초 |
| pp (새 입력 기준) | 104.49 tok/s | 68.09 tok/s |
| tg | 17.90 tok/s | 17.41 tok/s |

두 번째 대화는 새 입력 218토큰을 처리했다. pp에서 역산한 모델 입력 처리
시간은 약 3.20초이고 나머지 약 5.33초는 서버 큐 대기다. 앱은 첫 답변 후
제목 생성도 별도 모델 요청으로 실행하므로 바로 이어진 대화는 이에 영향을
받을 수 있다. 이 실제 앱 결과를 짧은 비추론 API 검사의 0.90초와 혼동하지 않는다.

저장된 답변의 pp/tg/ttft가 마지막 SSE 수치와 일치하는 것도 확인했다.
테스트 세션은 삭제했고 사용자 기억은 변경하지 않았다. 결과는
`compose_yaml/ds41f_vllm/results/sparktalk-prefix-validation.json`에 있다.

캐시 보존 정책을 바꾼 뒤 긴 문맥도 다시 검사했다. 54,988토큰 입력과
8,192토큰 출력 허용량으로 중간의 표식을 정확히 찾았고, HTTP 200과 정상
종료를 확인했다(첫 내용 수신 53.19초). 반복 문장으로 만든 용량 검사이며
일반 문서의 처리율 측정은 아니다. 결과 파일은
`results/prefix-context-capacity-validation.json`이다.

양쪽 rank의 옵션 128, KV 2 GiB, expert 텐서 87,836,590,080바이트와 정상
기동을 확인했다. 긴 문맥 검사 후 호스트 가용 메모리는 각각 약 13.2/13.4 GiB였다.
실행 옵션·소스/바이너리 해시는 `results/prefix-runtime-validation.json`에 있다.
여기서 `results/`는 모두 위 DeepSeek 레시피 디렉터리 기준이다.

## 한계

모델 재기동 직후, 다른 시스템 지침·도구 조합, 캐시 축출 이후, 긴 새 문서의
첫 처리에서는 여전히 많은 입력을 새로 처리한다. 새 대화라는 이유만으로 항상
캐시가 사라지는 것은 아니며, 실제 토큰 앞부분이 같고 캐시가 남아 있는지가
중요하다. 생성 속도 `tg`의 개선율로 이 측정값을 해석하면 안 된다.

화면 `pp`는 캐시 토큰을 제외한 새 입력의 처리율이다. 캐시가 잘 맞으면 실제
대기시간이 크게 줄어도 표시되는 `pp`가 같은 비율로 높아질 필요는 없다.


## 후속 pp 개선

서빙 엔진의 버퍼 공유와 native 2048-token expert 계산으로, 동일한 비캐시
입력의 pp가 약 144→158 / 171→193 tok/s로 개선됐다. 이는 SparkTalk 프롬프트
축약이나 추가 양자화가 아니다. 구현·실측·제외한 후보는
[엔진 실험 기록](../../../compose_yaml/ds41f_vllm/docs/PREFILL_ARCHITECTURE.md)에 있다.


이어진 4096 배치 재시험은 새로 고정한 동일 입력에서 pp 159→193 / 191→241 tok/s,
ttft 39.6→32.7 / 67.8→53.6초였다. 실제 Talk의 재기동 후 첫 요청도 35.3초에
생성을 시작했다. [재시험과 검증 기록](../../../compose_yaml/ds41f_vllm/docs/PREFILL_4096_RETRY.md)을 참조한다.


마지막 decoder 레이어의 routed expert 계산을 줄이는 후속 실험은 pp가
약 2% 개선됐지만, 동일 출력의 tg가 26.82→24.69 tok/s로 7.96% 감소했다.
따라서 기본 적용하지 않고 기존 서빙 설정을 유지했다. DSpark 내부 상태,
캐시 재사용, 동일 출력 비교와 제외한 측정은
[decoder 실험 기록](../../../compose_yaml/ds41f_vllm/docs/DECODER_ROWS_EXPERIMENT.md)에 있다.
