# 답변별 pp · tg · ttft

답변 아래에 소문자 `pp`, `tg`, `ttft`를 표시한다. 속도 단위는 `tok/s`,
시간은 `s`다. 값이 없거나 계산할 수 없는 단일 토큰 응답은 `—`로 표시한다.
진행 중 추정값과 서버 시간 통계가 없는 연결의 추정값에는 `≈`를 붙인다.
값 위에 마우스를 올리면 계산 범위, 추정 여부, 캐시 재사용량을 볼 수 있다.

## 계산 범위

- `pp`: 새로 처리한 입력 토큰 수 / 입력 처리 시간. 서버가 알려준 캐시
  재사용 토큰을 제외한다. 캐시 정보나 서버 처리 시간이 없으면 추정값이다.
- `tg`: 추론·답변·도구 호출을 포함한 생성 토큰의 속도. 검색, 도구 실행,
  승인 대기와 입력 처리 시간은 제외한다. SSE 청크 수를 토큰 수로 세지 않는다.
- `ttft`: 첫 모델 호출의 첫 생성 토큰까지 걸린 시간. 추론 토큰도 포함한다.
  서버 측 수치는 모델 대기열 시간을 포함하며, SparkTalk의 사전 문맥 정리나
  네트워크 왕복 전체를 뜻하지는 않는다. 서버 통계가 없으면 첫 비어 있지 않은
  추론·답변·도구 이름/인자 이벤트의 수신 시간으로 추정한다. 역할/빈 이벤트는 제외한다.

도구 라운드·출력 연장·빈 답변 복구로 여러 모델 요청이 발생하면 `pp`와 `tg`는
각 요청의 토큰 수와 해당 처리 시간을 더해서 계산한다. 요청별 속도의 단순
평균이나 전체 대화 경과 시간을 사용하지 않는다. `ttft`는 첫 요청의 값을 유지한다.
제목 생성과 별도 요약 요청은 답변의 생성 속도에 포함하지 않는다.

## 백엔드 통계

현재 DeepSeek V4.1용 고정 vLLM 이미지에는 다음 옵션을 활성화했다.

```text
--enable-per-request-metrics
--enable-prompt-tokens-details
```

`stream_options.include_usage=true`의 마지막 usage 이벤트에서 `metrics`와
`prompt_tokens_details.cached_tokens`를 받는다. 현재 이미지의 시간 의미는
실제 설치된 `build_per_request_timing_metrics` 구현으로 확인했다.

- `time_to_first_token_ms`: 스케줄된 시점부터 첫 토큰까지. pp의 처리 시간이다.
- `queue_time_ms`: 큐 대기 시간. 화면 ttft에는 앞의 시간과 합해서 사용한다.
- `generation_time_ms`: 첫 토큰부터 마지막 토큰까지. tg는
  `(completion_tokens - 1) / (generation_time_ms / 1000)`으로 계산한다.
- `tokens_per_second`: 입력 처리까지 포함한 전체 출력 처리율이므로 tg에 사용하지 않는다.

서버가 llama.cpp 형식 `timings`를 제공하면 `prompt_n/prompt_ms`와
`predicted_n/predicted_ms`를 사용한다. 공통 API에 추가 요청 필드를 무조건
붙이지 않으므로 다른 연결은 기존 요청 형식을 유지한다.

서버 통계가 없는 경우 최종 usage 토큰 수와 클라이언트 수신 시간을 사용하되
`≈` 표시를 유지한다. 생성 중에는 ASCII 문자당 0.25, 기타 문자당 1토큰의
거친 추정치를 쓴다. 이는 언어별 토크나이저를 대체하는 정확한 수치가 아니다.
서버 usage/시간 통계가 도착하면 해당 추정치를 덮어쓴다. 갱신은 최대 초당4회다.

## 저장과 화면

`internal/performance`가 요청별 측정치를 합산하고, LLM 스트림 관찰자가
`performance` SSE 이벤트를 보낸다. 응답 완료 시 확정된 요약을 응답 버전의
기존 JSON에 함께 저장한다. DB 컬럼 추가나 과거 답변의 가짜 수치 생성은 없다.

일반 답변, 재시도, 수정 분기, 중단된 부분 답변에 대응한다. 버전을 바꾸면 그
버전의 수치를 표시하고, 예전처럼 측정값이 없는 버전으로 돌아가면 숨긴다.
실패한 재시도에서는 기존 답변과 기존 수치를 함께 복구한다.

검증: 토큰 묶음 스트림, 캐시 제외, 대기와 생성 시간 분리, 라운드별 가중 합산,
단일 토큰/없는 값, DB 재개방 후 버전별 복원, 중단 응답 저장을 검사했다.
브라우저에서는 1280px/390px 화면, 버전 전환, 새로고침과 기존 잘림 응답 표시를
확인했다. 실제 모델 연결 검사 결과는 별도 로컬 검증 기록에 보관한다.

반복 요청의 첫 토큰 지연을 줄이는 프롬프트 배치와 vLLM 설정은
[입력 캐시 개선 기록](prefix-cache-latency.md)에 설명한다. 캐시를 제외하는
`pp` 계산은 유지하므로 대기시간 감소율과 표시 처리율 증가율은 다를 수 있다.
